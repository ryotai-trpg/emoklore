# テスト方針

テストに関する規約はここが正（SSOT）。型と設計の規約は [コード設計の規約](/code-design)、セットアップやコミット規約は [コントリビュートガイド](/contributing) にある。

検証は2段ある。**Foundryが要らないものは vitest、要るものは実機検証**。この線引きが方針の全部で、迷ったら「本体を起動しないと確かめられるか」を考える。

| | 単体テスト | 実機検証 |
|---|---|---|
| コマンド | `npm test` | `npm run verify:live` |
| 置き場所 | 対象と同じディレクトリ | `tests/live/` |
| 対象 | Foundry非依存の純粋関数 | 起動しないと分からないこと |
| CI | 回す | **回さない** |
| 所要 | 0.2秒 | 7秒 |

## 単体テスト

[Vitest](https://vitest.dev/) を使う。テストは**対象と同じディレクトリ**に `*.test.ts` として置く。

```shell
npm test        # 一度だけ実行
npx vitest      # ウォッチモード
```

対象は**FoundryVTT APIに依存しない純粋関数**（判定計算・ポイント計算・書式整形など）に限る。Foundry本体のクラスを継承・参照するコードはランタイムに本体が必要なので、ここでは扱わない。逆に言えば、**テストしたいロジックはFoundry非依存の形に切り出す**。

`vitest.config.ts` は `environment: "node"` にしてある。`game` や `ui` に触れば落ちるので、純粋性は設定が構造的に守っている。

同じ場所に置くのは、**テストの配置がそのまま「どこが純粋か」の地図になる**ため。`rules/` は全ファイルに `.test.ts` が並び、`utils/` は1つしか無い。この偏りが見えることに意味がある。

## 実機検証

本体を実際に起動し、ヘッドレスChromeでシステムを動かす。

```shell
npm run verify:live
```

**専用の検証環境が要るのはこのコマンドだけ。** `npm run dev`（proxy先のFoundry本体）も `npm run typecheck`（本体ソースの参照）も、普段使いのFoundry（`localhost:30000`）とそのインストール先のままで足りる。検証はデータを作って消すためメイン環境には向けられず（後述）、専用環境を別に用意する。作り方は[検証環境のセットアップ](#検証環境のセットアップ)にある。

**CIでは回さない**（理由は[下記](#ciで回さない理由)）。各自の環境で実行する。

配置は環境変数で指す。**既定値のままで動くなら何も要らない。** 違うところだけ書きたい場合は雛形をコピーする。

```shell
cp .env.example .env   # git管理外。書いた項目だけが効く
```

`.env` は無くてもよく、無いときは黙って既定値を使う。**環境変数を直接指定したほうが `.env` より優先される**ので、`FVTT_PORT=30015 npm run verify:live` のような一時的な上書きがそのまま効く。

既定値は**作者のローカル運用**（本体は `~/FoundryVTT/` 配下、ポートは「300 + 世代番号」、ワールドは `emoklore-test`）であって、リポジトリの決まりではない。同じ配置を持っている必要はなく、自分の環境に合わせて `.env` で上書きする。

| 変数 | 既定 | 何を指すか |
|---|---|---|
| `FOUNDRY_APP` | `~/FoundryVTT/v14/code` | 本体のNode配布版（`main.mjs` のあるディレクトリ） |
| `FVTT_DEV_DATA` | `~/FoundryVTT/dev-data-v14` | 検証専用のdataPath |
| `FVTT_PORT` | `30014` | 300 + 世代番号 |
| `FVTT_WORLD` | `emoklore-test` | 検証用ワールド |
| `FVTT_USER` | `Gamemaster` | ログインするユーザー名 |
| `SKIP_BUILD` | — | `1` でビルドを省く |
| `CHROME_BIN` / `CDP_PORT` | 自動探索 / `9223` | Chromeの実行ファイルとデバッガのポート |

**`FVTT_DEV_DATA` にメイン環境のデータを指さないこと。** 検証はアクター・シーン・トークンを作って消すので、遊んでいるワールドに向けてはいけない。ポート30000も同じ理由で弾いており、`.env` に書いても前提確認で落ちる。

### 検証環境のセットアップ

前提が足りないと `verify:live` は着手前にエラーの一覧で止まる。各メッセージに対応する手順は以下。すべて一度きりの作業で、以後はコマンド一発で通る。

1. **本体のNode配布版を置く**（「FOUNDRY_APP に main.mjs が無い」）

   [foundryvtt.com](https://foundryvtt.com/) の購入者ページから **Linux/NodeJS** 版をダウンロードして展開し、`main.mjs` のあるディレクトリを `FOUNDRY_APP` に指す。世代はシステムの compatibility（v14）に合わせる。デスクトップアプリはヘッドレス起動とポート指定ができないので代用できない

2. **検証専用の dataPath を作る**（「FVTT_DEV_DATA が無い」）

   空のディレクトリを作って `FVTT_DEV_DATA` に指す。中身（`Config` / `Data` / `Logs`）は初回起動時に作られる。ライセンスは初回起動の画面でキーを入れるか、メイン環境の `Config/license.json` をコピーする

3. **システムを配置する**（「システムが配置されていない」）

   `dist/` をビルドし、dataPath の `Data/systems/emoklore` から symlink を張る

   ```shell
   npm run build
   mkdir -p <FVTT_DEV_DATA>/Data/systems
   ln -s "$(pwd)/dist" <FVTT_DEV_DATA>/Data/systems/emoklore
   ```

4. **検証用ワールドを作る**（「ワールドが無い」）

   一度手で起動し、ブラウザでセットアップ画面からワールドを作る（システムは emoklore）。作ったワールドのID（`Data/worlds/` のフォルダ名）を `FVTT_WORLD` に指す

   ```shell
   node <FOUNDRY_APP>/main.mjs --dataPath=<FVTT_DEV_DATA> --port=30014
   ```

   セットアップ画面に入るための管理者アクセスキーは、この初回起動の画面で設定する（未設定でも入れる。検証自体はワールドへの参加しかしないのでどちらでもよい）

### 構成

```
.env.example           環境変数の雛形（コピーして .env を作る）
tests/live/
  run.mjs              エントリ。checks/ を順に回す
  lib/cdp.mjs          依存ゼロのCDPドライバ
  lib/config.mjs       環境変数
  lib/foundry.mjs      前提確認・起動・ログイン
  lib/fixtures.mjs     検証用データの作成と後片付け
  lib/harness.mjs      チェックの実行と集計、ページ側に仕込む道具
  checks/*.mjs         機能ごとの検証
```

**検証を足すときは `checks/` にファイルを作り、`run.mjs` の `CHECKS` に並べる。** 1ファイルが1つの機能に対応する（登録・スキーマ・キャラクターシート・判定・武器・取り込み・総合）。ファイルは `title` と `run({ page, check })` を export する。

### 規約

- **検証用データは毎回作って毎回消す**（`__verify` 接頭辞）。ワールドの手作りデータに依存すると他人の環境で落ちる
- **ダイスは `CONFIG.Dice.randomUniform` を差し替えて固定する**。固定しないと「攻撃が外れたのでダメージが振れない」を不具合と区別できず、実行ごとに結果が変わる。固定できるので、外れる出目に振って「命中しなければダメージを振れない」も検証できる
- **待機は固定時間ではなく条件で行う**（`__waitFor`）。`setTimeout` で待つと待ち時間の総和がそのまま実行時間になるうえ、遅い環境では足りずに落ちる。例外は「何も起きないこと」を確かめる箇所だけで、そこは条件で待てないので短い固定時間を置く
- **ルールの計算式そのものは検証しない**。それは単体テストが持つ。ここで見るのは配線が生きているかどうか
- 前提が足りなければ**着手前に落とす**。途中で落ちた場合も、通ったぶんだけ報告したうえで失敗として終わる（「1件も実行されなかった」を成功と見分けられなくしない）

### 何を見ているか

単体テストでは届かないものに限る。

- **登録の整合**: `system.json` の `documentTypes` と `CONFIG.*.dataModels` が食い違っていないか。`trackableAttributes` の参照先がスキーマに実在するか
- **スキーマ**: キーが `CONFIG.EMOKLORE` と一致するか。派生値が入力に追随するか
- **描画**: シートの全パートが描けるか。**未解決の翻訳キーが画面に出ていないか**
- **操作**: 4経路のロールが飛ぶか。武器カードが 攻撃 → ダメージ → 適用 と進むか
- **壊れた入力**: DOMの綴り間違いや欠けたJSONで例外にならないか
- **設定**: 自動化のつまみを切ったときに、実際に自動処理が止まるか（既定の側は他のチェックが通ることで確かめられているので、切った側だけを見る。触った設定は必ず元へ戻す）
- **総合**: コンソールエラーと想定外の警告通知が無いか

### 翻訳キーの検査

3つに分かれていて、見る範囲が違う。

| | 見るもの | 見ないもの |
|---|---|---|
| `check:lang` | `ja.json` と `en.json` のキー集合と並び順 | 値。訳し忘れて日本語が残った `en.json` は通る |
| `check:i18n` | キーと参照側（`templates/` `module/` `system.json`）の突き合わせ。未定義キーの参照と、どこからも参照されないキー | 実際に描いたときに解決するか |
| `verify:live` | 描いた画面に未解決のキーが出ていないか | — |

`check:i18n` が拾えるのは、**キーが `EMOKLORE.` か `SETTINGS.EMOKLORE.` で始まるもの**だけ。`TYPES.` `USER.` `DOCUMENT.` は本体と名前空間を共有していて、本体側で解決するキーを引いている可能性があるため、未定義の判定には使わない。

動的に組み立てるキー（`` `EMOKLORE.Result.${name}` ``）は手書きのallowlistを持たず、**テンプレートリテラルの静的な部分からパターンを起こして**扱う。書き換えれば自動で追従し、1件も当たらなくなったら綴り間違いとして落ちる。

`LOCALIZATION_PREFIXES` や `TABS` の `labelPrefix` のように**名前空間そのものを渡す**場合は、配下の何を読むかを決めるのは本体なので静的に追えない。参照された名前空間の配下は、まとめて「使われている」とみなす。

### ドキュメントの検査

`check:schema-doc` は [データモデル](/data-model) と [効果（ActiveEffect）](/active-effect) が並べているキーと日本語名を、`module/config/` のテーブルおよび `lang/ja.json` と突き合わせる。**コードは型で綴りを守れるが、ドキュメントには型が無い**ので、同じ間違いがドキュメント側にだけ残る。

configのテーブルは型だけをimportしていてFoundryに依存しないため、Nodeが `.ts` をそのまま読める。`erasableSyntaxOnly` が型剥がし可能であることを保証しているので、ローダもビルドも要らない。

### CIで回さない理由

**技術的にできないからではない。** CIはすでに `tools/fetch-foundry.mjs` で本体を落としており（`typecheck` ジョブ）、Chromeも `ubuntu-latest` に入っている。そのうえで見送っている。

- **secretsが要るジョブはフォークPRで動かない。** `typecheck` が同じ理由でフォークPRをスキップしている（公開リポジトリのActions cacheはフォークからrestoreできるため）。実機検証の価値が最も高いのは事情を知らない人が触ったときで、それがまさに動かないケースになる。**ゲートとして機能しないうえ、CIが緑なので「検証済み」と誤解される**
- **ダウンロードと起動は別物。** 型チェックは `client/` と `common/` のソースを読むだけだが、サーバの起動にはアクティベート済みの `Config/license.json` が要る。つまりライセンスキーをGitHub secretsに置くことになり、**ライセンス的に微妙**

入れるとしたら「PRのゲート」ではなく「マージ後の見張り」として `push: [develop]` と `workflow_dispatch` に限る形になるが、ライセンスの件が解決しない限り採らない。

**CIが見てくれないぶん、人が回す。** マージ前とリリース前に `npm run verify:live` を通すこと。

## チェックが本当に落ちるかを確かめる

**通ったことより、壊したときに落ちることのほうが重要。** 検証を足したら、それが検出するはずの不具合をわざと入れて、NGになることを確かめる。

素通りするチェックは簡単に書けてしまう。要素が見つからないのに `?.click()` で流す、`render()` を待たずに古いDOMを数える、非リンクトークンの合成アクターではなくワールドのアクターのHPを見る — いずれも「okと出るが何も確かめていない」状態になり、わざと壊すまで気付けない。**チェックを書いたら、必ず一度は赤くしてみること。**
